# Architecture

How this repository turns a folder of TOML files into the track titles shown by every copy of
[Soundfolk](https://github.com/getsoundfolk/soundfolk).

## 1. The problem
Many web radios do not announce the track on air in their stream (no ICY `StreamTitle`, no Ogg
tags), but show it on their website: a player page, a "titres diffusés" list, a JSON API used by
their own web player. A **recipe** says, for one station, which page to read and where the track is
on it. Recipes are **data, not code**: one URL, CSS selectors, dotted JSON paths or one regular
expression. No scripting, no credentials, nothing the app runs.

## 2. Overview

```
 contributors                     this repository                         GitHub Pages
 ────────────                     ───────────────                         ────────────
 stations/<id>.toml  ──PR──▶  CI: lint + recipe-check test  ──merge──▶  CI: recipe-check compile
 fixtures/<id>.html                                                       └▶ v1/recipes.json
                                                                             v1/recipe.schema.json
                                                                                    │
                                                         once a day, If-None-Match  │
 Soundfolk app ◀─────────────────────────────────────────────────────────────────────┘
   local recipes  >  shared list (cached)  >  recipes shipped in the app
           │
           └─ while a station plays: fetch the recipe's page, extract the track, schedule the next read
```

1. A contributor adds `stations/<id>.toml` and a saved excerpt of the page in `fixtures/`: usually
   from the app (*Share this recipe*, which opens an issue a bot turns into a pull request), or by
   hand.
2. On every pull request, CI validates the recipes and replays each recipe against its fixtures.
3. On every push to `main`, CI compiles all recipes into one JSON file and publishes it on GitHub
   Pages.
4. The app downloads that file once a day, caches it, and uses it whenever a stream does not
   announce its titles.

## 3. Repository layout

| Path | What |
|---|---|
| `stations/<id>.toml` | One recipe per station. The file name is the recipe's **id**. |
| `fixtures/<id>*.html`, `.json`, `.txt` | Excerpts of the pages, replayed by the tests. |
| `recipe.schema.json` | JSON Schema of the recipe format, for editor completion (Taplo reads the `#:schema` line). Generated by `recipe-check schema`. |
| `scripts/lint.py` | Repository rules the recipe engine does not know about (names, fixtures, duplicates). |
| `scripts/from_issue.py` | Writes the recipe and fixture of a *Share a recipe* issue into `stations/` and `fixtures/`. |
| `.github/workflows/recipes.yml` | Checks, publication, weekly live check. |
| `.github/workflows/share.yml` | Turns a *Share a recipe* issue into a pull request. |
| `.github/actions/recipe-check/` | Builds and caches `recipe-check` from the app's repository. |

### Recipe ids
The id is the file name without `.toml`: lowercase ASCII letters, digits, `-` and `_`
(`frequence7`, `radio-nova`). It is stable: the app uses it to let a user's own file **replace** a
shared recipe (same id), whatever its `match` says. Renaming a file therefore breaks the local
overrides people made of it; fix recipes in place instead.

### Fixtures
A fixture is the part of the page the recipe reads, saved at a known instant, with what the recipe
must find in it (`[[test]]`): artist, title, start time, next track. They are third-party content
and are **not** covered by the database licence (see `LICENSE`). Keep them small (64 KiB max) and
stripped of everything else (scripts, trackers, personal data).

## 4. The recipe engine lives in the app
The format, the extraction and the scheduling are implemented once, in the
[`soundfolk-nowplaying`](https://github.com/getsoundfolk/soundfolk/tree/main/src-tauri/crates/nowplaying)
crate of the app's repository: a library with no I/O (the host fetches pages and passes them in).
Its `recipe-check` binary is what CI and contributors run:

```text
recipe-check validate <recipe.toml>...        check the format
recipe-check test <recipe.toml>...            replay each recipe's [[test]] fixtures
recipe-check run <recipe.toml> [--page FILE] [--at RFC3339]
                                              show what the recipe reads now (live without --page)
recipe-check fixture <recipe.toml> [--page FILE] [--at RFC3339]
                                              save the excerpt the recipe reads in ../fixtures/ and
                                              write its [[test]] (live without --page)
recipe-check compile <dir> [-o recipes.json]  build the published list
recipe-check schema                           print the JSON Schema
```

CI builds it from the app's `main` branch (cached per commit), so this repository always checks
recipes with the engine the next release of the app will ship. The format reference is
[`docs/07-now-playing.md`](https://github.com/getsoundfolk/soundfolk/blob/main/docs/07-now-playing.md).

## 5. Continuous integration
`.github/workflows/recipes.yml` has three jobs.

| Job | When | What |
|---|---|---|
| `check` | every pull request and push | `scripts/lint.py`; `recipe-check test stations/*.toml`; compile the list and attach it to the run; warn when `recipe.schema.json` is behind the engine. |
| `publish` | push to `main`, manual on `main` | compile, then deploy `v1/recipes.json` and `v1/recipe.schema.json` to GitHub Pages. |
| `live` | Mondays, manual on `main` | read every station's page **now** with `recipe-check run` and list in the run summary the recipes that find nothing. Never blocks anything: sites change, pages are empty between shows. |

`share.yml` runs on issues labelled `shared-recipe` (opened or edited): see *Sharing from the app*.

`lint.py` enforces what the engine cannot see from one file:
* file names are valid ids, and each recipe starts with `#:schema ../recipe.schema.json`;
* each recipe has at least one `[[test]]` whose page is in `fixtures/` and at most 64 KiB;
* every fixture is used by a recipe;
* no two recipes claim the same stream or the same Radio-Browser station (the app would silently use
  the first one by file name).

## 6. Sharing from the app
Contributing should not require git, curl or Rust. The station sheet in Soundfolk (ⓘ in the
player) has two buttons for it:

* **Ask for a recipe**, when no source gives the title: opens the `station.yml` issue form filled in
  with the station's name, its Radio-Browser page, the stream and the website.
* **Share this recipe**, on a local recipe (written with *Create a recipe* or *Edit locally*):

```
 app                                      GitHub                               this repository
 ───                                      ──────                               ───────────────
 read the page now (+ HTTP Date)
 excerpt = what the recipe reads  ──▶  issue form "Share a recipe"  ──▶  share.yml:
 [[test]] = what it reads there        (recipe, fixture, id, licence)      from_issue.py → stations/, fixtures/
 open the form, filled in                                                  lint.py + recipe-check test
                                                                           ok: branch share/issue-<n>, pull request
                                                                               in the issue author's name, checks run
                                                                           not ok: comment, edit the issue to retry
```

* **The fixture** is built by the engine (`soundfolk_nowplaying::fixture`, also behind
  `recipe-check fixture`): the elements the recipe reads (the item, the first three upcoming tracks,
  the show) with the chain of their ancestors and their attributes, so that the selectors still
  match; for JSON, the paths read in an otherwise empty document; for text, the match. The excerpt
  must read exactly like the whole page, else a wider one is tried (whole parents, for positional
  selectors such as `:nth-child`), else the contributor is told to save it by hand. Scripts, styles,
  navigation and comments never make it in.
* **The test** is what the recipe reads in the excerpt, at the page's HTTP `Date`. The recipe file
  keeps its comments; its earlier tests are replaced.
* **The link** carries the recipe and the fixture in the form's fields. A link over 7500 characters
  leaves the fixture out and puts it in the clipboard instead, to paste. The app also keeps both
  files in `<recipes folder>/to-share/`, laid out as here, for a pull request by hand.
* **The workflow** treats the issue body as untrusted: it only writes it to the two files and never
  puts it on a command line; it runs the default branch's scripts. Pull requests opened with the
  workflow's token do not trigger workflows, so it starts `recipes.yml` on the branch itself
  (`workflow_dispatch`, which `publish` and `live` ignore outside `main`). The commit is authored by
  the issue's author, from their GitHub `noreply` address. An existing id updates that recipe: the
  usual way to propose a fix.

Repository settings this needs: the `shared-recipe` label, and *Allow GitHub Actions to create
pull requests* (organization, then repository: Settings › Actions › General). Without the latter,
the workflow still pushes the branch, runs the checks and comments a link that opens the pull
request prefilled, for a maintainer to click.

## 7. The published list
`https://getsoundfolk.github.io/soundfolk-recipes/v1/recipes.json`

```json
{
  "schema": 1,
  "recipes": [
    { "id": "frequence7", "schema": 1, "name": "Fréquence 7",
      "match": { "streams": ["live.aurafm.org/Frequence7"] },
      "fetch": { "url": "https://www.frequence7.net/player/" },
      "extract": { "type": "html", "item": "li.event_0", "artist": ".artist", "title": ".title", "…": "…" } }
  ]
}
```

* Compact JSON (shown indented above; `jq .` to read it), served gzip-compressed by GitHub Pages and
  revalidated with its `ETag`: an unchanged list costs a `304`.
* Recipes **without their tests** (fixtures stay here), each with its `id`.
* `v1` is the version of the **list** format. Each recipe still carries its own `schema`: a recipe
  written for a newer format is skipped by older apps, one by one, without breaking the others. A
  breaking change of the list itself would be published under `v2/`, next to `v1/`, so that apps
  already installed keep working.
* Compilation fails if any recipe is invalid: the published list is always readable as a whole.

## 8. In the app
Implemented in `src-tauri/src/recipe_list.rs` and `src-tauri/src/recipes.rs`.

* **Download.** At most once a day, only while "Find the track on air on the station's website" is
  on (⚙ › Privacy), with `If-None-Match`: an unchanged list costs a `304`. GitHub sees the
  listener's IP address. `SOUNDFOLK_RECIPES_URL` points the app at another list (a fork, a local
  server) for testing.
* **Cache.** The last list is kept in the app's cache folder and used at startup, offline
  included. A download that does not parse is ignored; the cached list stays.
* **Priority**, by id: the user's own files (`<config dir>/recipes/<id>.toml`) > the shared list >
  the recipes shipped inside the app (a snapshot used before the first download). A recipe replaces
  the ones with the same id below it; otherwise the first whose `match` fits the station wins.
* **Switching.** When the list changes, the station playing moves to its new recipe without
  interrupting the sound.
* **Editing.** The station sheet (ⓘ in the player) says which recipe is in use. *Edit locally*
  copies a shared recipe into the user's folder, where it replaces the shared one on that device:
  the usual way to fix a recipe before proposing the fix here with *Share this recipe* (section 6).

## 9. What the app enforces, whatever a recipe says
A recipe cannot make the app hammer a site: at least 15 s between requests, at most 120 per hour,
random jitter, backoff on errors, and roughly one request per track when the page gives start times
or durations. A page is only read while someone listens to that station.
